# Подготовка к публикации (`dist/`)

Правило, по которому проект готовится к выгрузке на хостинг. На хостинг уходит только
содержимое папки `dist/` — никогда не корень проекта (там `docs/`, исходники, `.git`).

## Обязательное правило подготовки

При запросе «подготовить к публикации» выполняется один и тот же порядок:

1. Проверить адрес и режим индексации в `config/deploy.php`. Без адреса разрешена
   предварительная сборка с `noindex: true`; выдумывать домен нельзя.
2. Изменять только исходники. Запустить `php bin/build-dist.php`; результат — `dist/`.
3. Проверить, что CSS объединён по точкам входа, JS-модули собраны по зависимостям,
   а ссылки на каждый итоговый CSS/JS содержат `?v=` с хэшем содержимого.
4. Проверить `dist/.htaccess`: на Apache HTML и статика перепроверяются сервером,
   долгий кеш отключён. На другом хостинге проверить его собственные правила кеша.
5. Проверить состав `dist/`: только страницы, используемые ресурсы и файлы из `deploy/`.
   Не копировать всю папку `assets/img/`, исходные модули или документацию.
6. Открыть именно собранный сайт, проверить меню, корзину, адаптив, консоль и Network.
   Проверить SEO/ИИ-чек-лист ниже и оба файла `llms*.txt`.
7. Передать путь к `dist/`, результаты проверок и оставшиеся настройки хостинга.
   Подготовка не означает автоматическую публикацию.

### Запуск сборки

```bash
php bin/build-dist.php
```

Скрипт каждый раз удаляет `dist/` и собирает её заново. Руками в `dist/` ничего
не правится: любое изменение вносится в исходники, потом сборка запускается снова.
`dist/` не хранится в git (`.gitignore`) — это артефакт, его всегда можно пересобрать.

Перед первой сборкой укажи адрес сайта в `config/deploy.php`:

```php
'site_url' => 'https://example.ru',  // без слэша и пути в конце
```

Пока `site_url` пуст или указан с путём — сборка останавливается с ошибкой, а старая
`dist/` не удаляется: без адреса нельзя собрать `sitemap.xml` и `robots.txt`.

### Предварительная сборка (`noindex`)

Если домена ещё нет или сайт выкладывается на технический/тестовый адрес, в
`config/deploy.php` ставится `'noindex' => true`. Тогда сборка:

- работает и без `site_url`;
- кладёт `robots.txt` с `Disallow: /` и добавляет на каждую страницу
  `<meta name="robots" content="noindex, nofollow">`;
- не создаёт `sitemap.xml`; `llms.txt` и `llms-full.txt` создаются с уведомлением о noindex;
  без домена ссылки в них относительные, ссылка на отсутствующий sitemap не добавляется;
  без `site_url` не добавляет `canonical`
  и `og:url`, адреса в OG и JSON-LD остаются относительными;
- в конце печатает предупреждение, что сборка предварительная.

SEO-проверка страниц при этом выполняется как обычно. Перед боевым запуском — указать
`site_url`, вернуть `'noindex' => false` и пересобрать: иначе сайт не попадёт в поиск.

### Архив для выгрузки

Если хостинг принимает архив (файловый менеджер панели умеет распаковывать zip), содержимое
`dist/` упаковывается в `site-dist-ГГГГ-ММ-ДД.zip` в корне проекта — вместе со скрытым
`.htaccess`, без `.DS_Store`:

```bash
cd dist && zip -qr -X ../site-dist-$(date +%F).zip . -x '.DS_Store' '*/.DS_Store'
```

Архив распаковывается **в корень сайта** (`public_html`, `www` и т. п.), а не в подпапку.
Архивы не хранятся в git (`.gitignore`).

Проверить собранный сайт локально — конфигурация `landing-dist` в `.claude/launch.json`
(`php -S localhost:8092 -t dist`).

## Что делает сборка

1. **Страницы.** Берёт все `*.html` из корня проекта и кладёт их в `dist/` с той же
   структурой путей. В разметке меняются только подключения CSS и JS (п. 2–4).
2. **CSS.** Каждый `<link rel="stylesheet" href="assets/…css">` — точка входа. Все `@import`
   встраиваются в один файл рекурсивно (каждый файл — один раз), относительные `url()`
   переписываются под место итогового файла, комментарии и отступы вырезаются.
   Результат лежит по тому же пути, что и точка входа: `assets/css/main.css` →
   `dist/assets/css/main.css`.
3. **JS.** Каждый `<script src="assets/…js">` — точка входа. Граф импортов от неё
   собирается в один файл: модули идут в порядке зависимостей, каждый — в своей
   области видимости, `import { … }` заменяется на чтение экспортов из уже выполненного
   модуля. Подключение остаётся `type="module"` (отложенная загрузка, strict mode).
4. **Версионирование.** К подключению собранных CSS и JS добавляется `?v=` — первые
   10 символов md5 от содержимого файла: `main.css?v=3f9a1c0b7e`. Поменялся файл —
   поменялась ссылка, браузер скачивает новую версию.
5. **Графика и прочая статика.** В `dist/` копируются **только** файлы, на которые есть
   ссылки: атрибуты `src`, `srcset`, `href`, `poster`, `data-src`, `data-srcset`,
   `content` в HTML; `url()` в собранном CSS; `href`/`url()` внутри скопированных SVG;
   `"src"` иконок в `*.webmanifest`; строки вида `'assets/….webp'` в собранном JS.
   Неиспользуемые картинки, варианты фавиконок, исходники и `docs/` в `dist/` не попадают.
6. **`sitemap.xml`.** Генерируется в корне `dist/` из всех страниц сборки:
   `index.html` → `{site_url}/`, остальные → `{site_url}/имя.html`. `lastmod` — дата
   изменения исходного HTML-файла. Страница с `<meta name="robots" content="noindex">`
   в sitemap не попадает.
7. **`robots.txt`.** Генерируется в корне `dist/`: индексировать всё (`Allow: /`) и строка
   `Sitemap: {site_url}/sitemap.xml`. Закрывать служебные пути не нужно — в `dist/` их нет.
   ИИ-краулеры (GPTBot, ClaudeBot, PerplexityBot, Google-Extended и др.) подпадают под
   `User-agent: *`, отдельные правила для них не нужны; в комментарии — ссылка на `llms.txt`.
8. **`llms.txt` и `llms-full.txt`** — файлы для ИИ-агентов, см. раздел «SEO и ИИ-агенты».
9. **SEO-теги.** В страницы `dist/` добавляются `canonical` и `og:url`, а относительные
   адреса в `og:image`, `twitter:image` и JSON-LD становятся абсолютными на `site_url`.
   Затем страницы проверяются на SEO-минимум, замечания печатаются в конце сборки.
10. **Корневые файлы хостинга.** Всё из папки `deploy/` копируется в корень `dist/` как есть:
   `.htaccess`, а при необходимости — `favicon.ico`, файлы подтверждения Яндекс Вебмастера /
   Google Search Console и т. п. Если в `deploy/` положить свои `robots.txt` или `sitemap.xml`,
   они заменят сгенерированные (например, чтобы закрыть тестовый домен от индексации).
   То же для `llms.txt` / `llms-full.txt`.
11. **Проверка.** Ссылка на несуществующий локальный файл — ошибка сборки с указанием файла,
   откуда идёт ссылка. Неполный `dist/` не выгружается.

В конце скрипт печатает список собранных и скопированных файлов и их размер.

## Правила для исходников, чтобы сборка работала

### CSS

- Подключение — только `@import url('./…');` (или `@import './…';`) в начале строки.
- `@import` с медиа-условием, абсолютные пути и пути за пределами проекта — ошибка сборки.
- Внешние `url()` (`https://…`, `data:`) остаются как есть.

### JS

Поддерживаемые формы (с начала строки):

- `import { a, b as c } from './x.js';` — фигурные скобки можно на несколько строк
- `import './x.js';`
- `export function`, `export async function`, `export const имя`, `export class`

Не поддерживается, сборка падает с указанием файла и строки: `export default`,
`export { … }`, `export … from`, `import x from`, `import * as`, `export let` / `export var`,
деструктуризация в `export const`, `import()`, `import.meta`, циклические импорты,
импорт не относительным путём (`'lib'`, `'/x.js'`, `https://…`).

### Ссылки на файлы

- В HTML — относительные пути от корня сайта: `assets/img/products/hero.webp`.
- Если JS подставляет картинку сам, путь пишется целиком строкой: `'assets/img/x.webp'` —
  иначе сборка её не найдёт и не скопирует.
- Картинка, которую не видит ни один из способов из п. 5, не попадёт на хостинг. Если
  такая нужна — добавь на неё ссылку в разметке или положи файл в `deploy/`.

## SEO и ИИ-агенты

Цель — чтобы поисковики и ИИ-агенты (ChatGPT, Claude, Perplexity, Алиса, Google AI)
правильно понимали, что это за бизнес, и цитировали точные факты: адрес, часы, цены.

### Что генерирует сборка

| Файл / тег | Что внутри | Откуда берётся |
|------------|------------|----------------|
| `llms.txt` | Предлагаемый формат [llmstxt.org](https://llmstxt.org): `# название`, `> описание`, список страниц и разделов со ссылками, ссылка на `llms-full.txt`; ссылка на `sitemap.xml` только в индексируемой сборке | Название — `og:site_name` (или `<title>` до « — »), описание — meta description, разделы — `<section id>` с `<h2>` внутри `<main>` |
| `llms-full.txt` | Весь текст страниц в Markdown: заголовки, абзацы, списки, ссылки абсолютными адресами | `<main>` и `<footer>` каждой страницы. Пропускается: `aria-hidden="true"`, `hidden`, `svg`, скрипты, картинки, кнопки, `.sr-only` внутри ссылок |
| `<link rel="canonical">` | Абсолютный адрес страницы | `site_url` + имя файла; если canonical уже есть в исходнике — не трогается |
| `<meta property="og:url">` | То же | Добавляется, если на странице есть другие `og:`-теги |
| Абсолютные адреса | `og:image`, `twitter:image`, поля `url`, `image`, `logo`, `@id`, `sameAs`, `hasMap` в JSON-LD | В исходнике пишутся относительными (`assets/…`, `./`), домен подставляет сборка |

Страницы с явным `noindex` в исходном HTML не попадают ни в `sitemap.xml`, ни в `llms.txt`.
Глобальный предварительный режим отличается: он закрывает обход, но позволяет проверить
`llms.txt` и `llms-full.txt` до публикации. В итоговый HTML включённых страниц сборка добавляет
`<link rel="describedby" href="llms.txt" type="text/plain">` для обнаружения описания.
Если все исходные страницы закрыты явным noindex, ИИ-файлы не создаются.
Свой `llms.txt` в `deploy/` заменяет сгенерированный.

`llms.txt` — дополнительное описание для агентов, а не гарантия индексации или цитирования.
[Google](https://developers.google.com/search/docs/appearance/ai-features) не требует
специальных ИИ-файлов для AI Overviews / AI Mode: нужны доступный для обхода сайт,
полезный контент и обычное SEO. Файл не отменяет meta robots, robots.txt или ограничения CDN.

### Обязательный SEO/ИИ-чек-лист при деплое

- **Адрес и доступность.** Проверить HTTPS, ответы 200 у страницы и ресурсов, один
  основной URL и canonical. Для GitHub Pages учесть подпапку репозитория во всех
  абсолютных ссылках; текущий сборщик требует расширения `site_url` перед индексацией
  project Pages. Не подставлять домен-заглушку.
- **Индексация.** Для готового публичного сайта согласованно выключить глобальный
  noindex, проверить meta robots, robots.txt и X-Robots-Tag на сервере. Проверить,
  что CDN не блокирует поисковых роботов и ресурсы. Для тестового сайта оставить noindex.
  На project Pages файл `/имя-репозитория/robots.txt` не заменяет robots.txt в корне
  хоста: отдельно проверить `/robots.txt`; meta robots страницы сохраняет значение.
- **Карты и агентские файлы.** Проверить sitemap только с каноническими индексируемыми
  страницами, реальные lastmod, существование llms.txt и llms-full.txt, рабочие ссылки
  и соответствие текста текущему HTML. Не добавлять в них секреты, внутренние документы
  или команды агентам, влияющие на ответы. Не поддерживать вторую ручную копию фактов
  без необходимости: основной источник — HTML.
- **Содержимое.** Уникальные title и description, один H1, логичная иерархия заголовков,
  alt, смысловые ссылки. Меню, цены, контакты и FAQ доступны в HTML без JS. Проверить
  актуальность сведений в JSON-LD типа CafeOrCoffeeShop и их совпадение с видимым текстом.
  Не добавлять вымышленные отзывы, рейтинги или расширенную разметку ради выдачи.
- **Краулеры.** Проверять поисковый доступ отдельно от разрешения обучения:
  [OAI-SearchBot](https://developers.openai.com/api/docs/bots) отвечает за поиск ChatGPT,
  GPTBot — за сбор для обучения. Политика для одного не заменяет политику для другого.
  Не добавлять разрешающие правила поверх тестового запрета индексации автоматически.
- **Скорость и мобильные.** Проверить Core Web Vitals через PageSpeed Insights,
  загрузку главного изображения, размеры картинок, lazy-loading ниже первого экрана,
  локальные шрифты, клавиатуру и отсутствие переполнения на 320px.
- **После публикации.** Подтвердить владение в Search Console и Яндекс Вебмастере,
  отправить sitemap, проверить URL Inspection и ошибки обхода. Для реальной кофейни
  добавить подтверждённые карточки Яндекс Бизнес / Google Business Profile с одинаковыми
  контактами. Для нынешних вымышленных реквизитов карточки не создавать.

В отчёте деплоя указать, что проверено автоматически, что вручную и что ещё требует
адреса, доступа к хостингу или подтверждённых бизнес-данных. Индексацию и появление
в ответах ИИ нельзя обещать по факту успешной сборки.

### Что должно быть в исходнике каждой страницы

Сборка проверяет это и печатает **SEO-предупреждения** (сборка не падает, но выкладывать
с предупреждениями — только осознанно):

- `<html lang>`; `<title>` до 70 символов; meta description 50–160 символов; ровно один `<h1>`;
  у всех `<img>` есть `alt`.
- Open Graph: `og:type`, `og:site_name`, `og:locale`, `og:title`, `og:description`, `og:image`
  (+ `og:image:width`, `og:image:height`, `og:image:alt`) и `twitter:card`.
- **`og:image` — JPG или PNG 1200×630** (1,91:1). Другой формат или пропорции — предупреждение:
  превью в мессенджерах обрежется или не покажется.
  Для главной — `assets/img/og-image.jpg`, собирается из шаблона `php bin/build-og-image.php`
  (см. `docs/design/og-image/README.md`). Поменялись оффер, цена или часы на первом экране —
  поправь шаблон и пересобери картинку.
- JSON-LD (schema.org) в `<script type="application/ld+json">` в `<head>`. Это данные, а не
  скрипт, поэтому правило «без inline-JS» на него не распространяется. Невалидный JSON —
  ошибка сборки. Тип — самый точный из schema.org под бизнес (`LocalBusiness` и его подтипы
  вроде `CafeOrCoffeeShop`, `Organization`, `Product`, `Service`, `Event`); для страницы
  с вопросами — дополнительно `FAQPage`. Для местного бизнеса: название, адрес, часы
  (`openingHoursSpecification`), цены, карта. Факты — только с самой страницы и из
  `product.md`, ничего не выдумывать; при изменении адреса, часов или цен на странице
  JSON-LD правится вместе с ними.

### Что ещё помогает SEO и ИИ-агентам (вне сборки)

- **Факты текстом, а не картинкой:** адрес, часы, цены, ответы FAQ — в HTML. Агенты
  читают текст; то, что нарисовано или появляется только после JS, они не видят.
- **Заголовки по смыслу:** `<h2>` раздела отвечает на вопрос человека («Доставка за 2 часа
  по городу — от 300 ₽»), а не «Доставка». Такие заголовки попадают в `llms.txt` как оглавление.
- **У каждой `<section>` — `id`**: на разделы можно сослаться (`/#menu`), они попадают в `llms.txt`.
- **Яндекс Вебмастер и Google Search Console:** подтвердить сайт (файл подтверждения —
  в `deploy/`), отправить `sitemap.xml`.
- **Яндекс Бизнес и Google Business Profile:** карточка организации с тем же названием,
  адресом и часами, что на сайте и в JSON-LD, — по ней поиск и ИИ сверяют данные.
- **Скорость:** уже обеспечивают сборка (один CSS, один JS), webp, `loading="lazy"`
  и предзагрузка шрифтов. Проверять в PageSpeed Insights после выгрузки.

## Кеширование (`deploy/.htaccess`)

Цель — чтобы после выгрузки посетители сразу видели новую версию, а не старую из кеша.

| Что | Заголовок | Почему |
|-----|-----------|--------|
| HTML | `Cache-Control: no-cache` | Браузер каждый раз сверяется с сервером (ETag / Last-Modified) — новые ссылки `?v=` на CSS/JS подхватываются сразу |
| CSS, JS | `public, no-cache, max-age=0, must-revalidate` | Хэш в `?v=` меняется при изменении файла; сохранённые копии дополнительно перепроверяются |
| Картинки, иконки, шрифты, манифест | `public, no-cache, max-age=0, must-revalidate` | Проверка актуальности при каждом обращении, в том числе при прежнем имени файла |

Дополнительно: сжатие текстовых форматов (`mod_deflate`), MIME-тип для `webp`, `svg`, `woff2`.
Блоки обёрнуты в `<IfModule>`, поэтому на хостинге без нужного модуля сайт не упадёт —
просто не будет этой настройки.

`no-cache` разрешает хранить копию, но требует проверить её актуальность перед использованием;
при неизменном файле сервер может ответить 304. Старый долгий кеш у уже посетившего сайт
браузера новые заголовки задним числом не отменяют: для срочной замены картинки меняется имя.

`.htaccess` работает только на Apache (или nginx + Apache). На чистом nginx эти правила
переносятся в конфиг сервера отдельно.

## Как публиковать

### GitHub Pages

Подготовлен `.github/workflows/pages.yml`: запуск вручную через Actions → Deploy Pages →
Run workflow. Сначала в Settings → Pages → Build and deployment выбрать **GitHub Actions**.
Workflow собирает проект PHP-скриптом и передаёт Pages только `dist/`, затем публикует артефакт.
Коммит и push выполняются отдельно; локальная подготовка workflow ничего не публикует.
В `dist/` не нужно добавлять исходные модули или хранить её в git.

Пути ресурсов относительные, манифест использует `./`: предварительная сборка работает
как на `https://имя.github.io/`, так и в подпапке репозитория.
Текущий режим — `noindex: true`, без canonical и sitemap: он сохраняется и в workflow.
Файлы llms.txt и llms-full.txt включаются и в этот режим с относительными ссылками.
Для включения индексации на адресе с подпапкой сначала нужно расширить проверку
`site_url` в сборщике: сейчас конфигурация допускает только домен без пути.

**На GitHub Pages `.htaccess` не исполняется.** Настроить Apache-заголовки этим файлом
там нельзя. CSS/JS обновляются за счёт `?v=хэш`; кеш картинок и шрифтов задаёт платформа.
Для немедленной замены такого ресурса следует менять имя файла и ссылки на него.
После публикации проверить фактические Cache-Control в Network.
Workflow следует [официальной схеме GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

### Apache-хостинг

1. В `config/deploy.php` указан боевой `site_url`; `php bin/build-dist.php` — сборка без ошибок.
2. Открыть `dist/` локально (`landing-dist`), пролистать страницу: стили, скрипты,
   все картинки и иконки на месте, в консоли нет ошибок и 404.
3. Выгрузить **содержимое** `dist/` (включая скрытый `.htaccess`) в корень сайта на хостинге.
4. Открыть сайт, проверить в DevTools → Network, что CSS/JS идут с `?v=` и с нужным `Cache-Control`.
5. Открыть `{site_url}/robots.txt`, `{site_url}/sitemap.xml` и `{site_url}/llms.txt`, добавить
   sitemap в Яндекс Вебмастер и Google Search Console.
6. Проверить разметку: превью ссылки — отправить её себе в Telegram;
   JSON-LD — [validator.schema.org](https://validator.schema.org) и
   [Rich Results Test](https://search.google.com/test/rich-results).

## Definition of Done

- [ ] `php bin/build-dist.php` проходит без ошибок
- [ ] В `dist/` нет `docs/`, исходных `.css`/`.js`-модулей и неиспользуемой графики
- [ ] Подключения CSS и JS в `dist/*.html` содержат `?v=`
- [ ] Сайт из `dist/` открывается без ошибок в консоли и без 404
- [ ] `dist/.htaccess` на месте
- [ ] `dist/robots.txt` и `dist/sitemap.xml` на месте, в них боевой домен, а не тестовый
- [ ] Для боевого запуска `noindex` в `config/deploy.php` выключен (в `dist/robots.txt` нет `Disallow: /`)
- [ ] Новая страница сайта появилась в `sitemap.xml` и `llms.txt` (или закрыта `noindex` намеренно)
- [ ] `dist/llms.txt` и `dist/llms-full.txt` на месте, текст в `llms-full.txt` читается без мусора
- [ ] SEO-предупреждений нет или каждое осознанно оставлено
- [ ] Факты в JSON-LD совпадают с текстом страницы
- [ ] SEO/ИИ-чек-лист выполнен; ограничения noindex, адреса и хостинга отражены в отчёте
- [ ] Ссылки из llms.txt ведут на существующие страницы/файлы; в предварительной сборке нет ссылки на отсутствующий sitemap
