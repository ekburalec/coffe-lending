# Стиль кода — PHP

> **Когда применяется.** Шаблон — статический HTML-лендинг без серверной части. Этот файл
> нужен, только если пользователь решил добавить её (обработка форм, админка, БД, загрузки).
> Тогда это отдельная фаза: стек и структура ниже, решение записывается в
> `docs/product/product.md` («Части системы»), а AGENTS.md дополняется разделом про PHP.
> Скрипты сборки в `bin/` — инструменты командной строки, на них этот файл не распространяется
> целиком, но стиль кода (функции, именование, обработка ошибок) — тот же.
>
> Документы, на которые ссылается этот файл и которых пока нет, создаются вместе с серверной
> частью: `docs/app/database-schema.md` (схема БД), `docs/modules/images.md` (обработка
> изображений и `responsive-image.tpl`), `config/images.php`.

## Назначение

Этот файл задаёт правила PHP-кода в проекте.
Цель — чтобы PHP-код оставался простым, читаемым, предсказуемым, поддерживаемым и легко контролировался при разработке с ИИ.

## Стек PHP

- PHP 8+
- SQLite
- PDO
- Роутер
- MVC
- Шаблоны в `templates/` с расширением `.tpl`

## Основной подход

- Предпочитаем простой процедурный PHP на функциях
- Не строим проект вокруг тяжёлого ООП
- ООП допускается только там, где это технически оправдано:
    - PDO
    - внешние библиотеки
    - небольшие инфраструктурные классы, если без них действительно не обойтись
- Бизнес-логика — простая и явная
- Код должно быть легко читать и править вручную

## Что используем

- функции
- понятную структуру файлов
- подготовленные запросы PDO
- простое разделение MVC
- явную валидацию
- явный роутинг
- рендеринг шаблонов через файлы `.tpl`

## Что не используем

- никаких лишних слоёв ООП
- никаких ORM
- никаких паттернов, завязанных на фреймворк
- никаких магических методов в основе архитектуры
- никакого оверинжиниринга
- никаких абстрактных классов и интерфейсов без реальной необходимости
- никаких скрытых побочных эффектов
- никакой логики в шаблонах
- никакого SQL в шаблонах

## Структура проекта

Основная структура PHP-части:

- `app/controllers/` — обработка запросов
- `app/models/` — запросы к базе и доступ к данным
- `app/services/` — обособленная логика приложения (загрузки, обработка редактора, работа с изображениями)
- `app/validators/` — валидация входных данных
- `app/helpers/` — вспомогательные функции
- `app/core/` — роутер, подключение к БД, рендеринг, запуск приложения
- `templates/` — шаблоны `.tpl`
- `config/` — настройки приложения, БД и маршрутов
- `index.php` — точка входа, фронт-контроллер

## Зоны ответственности

### Контроллеры

Контроллеры:

- принимают запрос
- читают входные данные
- при необходимости вызывают валидатор
- вызывают модель или сервис
- готовят данные для шаблона
- возвращают или рендерят ответ

Контроллеры не должны:

- содержать SQL
- содержать объёмную бизнес-логику
- генерировать HTML напрямую
- обрабатывать загруженные файлы на месте, если эту логику можно вынести

### Модели

Модели:

- работают с базой данных
- содержат SQL-запросы
- возвращают структурированные данные

Модели не должны:

- рендерить шаблоны
- содержать логику отображения
- содержать посторонние побочные действия

### Сервисы

Сервисы:

- содержат обособленную логику приложения
- обрабатывают файлы
- обрабатывают изображения
- очищают HTML текста с оформлением по белому списку перед сохранением
- содержат переиспользуемую логику сценариев

Сервисы не должны:

- рендерить шаблоны
- подменять собой контроллеры или модели

### Валидаторы

Валидаторы:

- проверяют входные данные
- при необходимости очищают их
- возвращают понятные ошибки

Валидация должна быть явной и читаемой.

### Шаблоны

Шаблоны:

- только выводят данные
- имеют расширение `.tpl`
- остаются простыми

Шаблоны не должны:

- содержать SQL
- содержать бизнес-логику
- содержать длинные цепочки условий
- менять состояние приложения

## Стиль кода

- пишем простой и прямолинейный код
- читаемость важнее изобретательности
- функции короткие
- вложенность минимальная
- там, где уместно, — ранний возврат
- без скрытой логики
- без больших универсальных хелперов без реальной необходимости
- один файл — одна основная ответственность

## Функции

Предпочитаем небольшие именованные функции.

Правила:

- имя функции ясно описывает действие
- функция делает одно дело
- без гигантских многофункциональных обработчиков
- передаём только нужные аргументы
- результат предсказуемый

Хорошо:

- `getPostBySlug()`
- `createPost()`
- `updatePost()`
- `validatePostData()`
- `saveUploadedImage()`

Плохо:

- `handleEverything()`
- `processData()`
- `run()`
- `doTask()`

## Именование

- в коде — понятные английские имена
- без случайных сокращений
- переменные, функции и файлы должны быть понятны
- один стиль именования на весь проект

Рекомендуется:

- `postTitle`
- `postSlug`
- `uploadedFile`
- `validationErrors`

Избегать:

- `data1`
- `tmpX`
- `resFinal`
- `a`, `b`, `c` — кроме крошечных локальных переменных цикла

## Правила для файлов

- один файл — одна ответственность
- связанная логика держится вместе
- не смешиваем в одном файле логику контроллера, модели и хелпера
- не дробим без нужды на множество микрофайлов

## Роутинг

- маршруты задаются централизованно
- роутер простой и явный
- в роутинге нет бизнес-логики
- запрос -> контроллер -> модель/сервис -> шаблон

## Правила работы с базой данных

- используем только SQLite
- доступ к БД — только через PDO
- только подготовленные запросы
- SQL явный и читаемый
- схема должна соответствовать `database-schema.md`

Нельзя:

- подставлять небезопасный пользовательский ввод в SQL конкатенацией
- прятать запросы за лишними абстракциями
- разбрасывать SQL по всему проекту

## Обработка ошибок

- ошибки обрабатываются предсказуемо
- внутренние ошибки не показываются пользователю напрямую
- ошибки валидации — понятные
- технические ошибки при необходимости пишутся в логи

## Правила безопасности

- проверяем весь внешний ввод
- очищаем там, где это уместно
- используем подготовленные запросы
- экранируем вывод в шаблонах
- проверяем загружаемые файлы по размеру, типу и расширению
- никогда не доверяем сырому пользовательскому вводу

## Данные из форм

- однострочные поля: `trim($_POST['name'] ?? '')`
- многострочные поля (`<textarea>`): `postText('content')` из `app/core/helpers.php`
- `postText()` обрезает пробелы и приводит переводы строк к `\n`
- браузеры всегда отправляют содержимое textarea с `\r\n`, в любой ОС — этого
  требует спецификация отправки HTML-форм, это не особенность Windows
- храним только `\n`: `\r` ломает побайтовое сравнение с сидами, диффами и тестами
  и добавляет лишний байт к каждому переводу строки при проверке длины
- `\r\n` возвращаем там, где его требует формат (HTTP-заголовки, email), — для почты
  это делает PHPMailer, а не контроллер

## Шаблоны и рендеринг

- шаблоны лежат в `templates/`
- расширение: `.tpl`
- рендеринг централизован
- контроллер передаёт в шаблон подготовленные данные
- шаблон выводит только то, что получил

## Редактор и контент

- текст с оформлением приходит из собственного поля `rich-text` (без WYSIWYG-библиотеки) и хранится как HTML
- HTML очищается на сервере при каждом сохранении одной сервисной функцией: `DOMDocument`,
  белый список `p h2 h3 blockquote strong b em i u s code a ul ol li hr br`, у ссылок — только `href`
  с `http`, `https` или `mailto` (решение D-08: очистка rich-text по белому списку)
- очистке на клиенте не доверяем никогда
- содержимое редактора обрабатывается в обособленной логике
- формат хранения явный и предсказуемый
- не смешиваем обработку сырого содержимого редактора с посторонними файлами

## Загрузки и изображения

- обработка изображений обособлена
- для растровых изображений используем GD
- растровые форматы: при загрузке принимаются jpg, png, webp; все генерируемые версии сохраняются в webp (`config/images.php`)
- SVG — для иконок и векторной графики
- для каждой растровой версии всегда готовим 2x-версию для retina (правило — в html.md, раздел «Изображения»)
- логика работы с файлами живёт в сервисах и хелперах, а не в шаблонах

## Правила PHP для ИИ

ИИ обязан:

- следовать этой структуре PHP
- соблюдать разделение ответственности MVC
- предпочитать функции и явную логику
- писать простой и читаемый код
- использовать подготовленные запросы PDO
- класть код в правильные папки
- не делать посторонний рефакторинг
- сохранять текущую архитектуру

ИИ не должен:

- вводить абстракции в духе фреймворков
- переписывать весь проект ради небольших изменений
- добавлять лишнее ООП
- смешивать ответственность слоёв
- помещать SQL в шаблоны и контроллеры
- придумывать новые решения по стеку без запроса

## Definition of Done

Реализация на PHP готова, когда:

- код соответствует заданной структуре проекта
- ответственность разделена правильно
- контроллеры остаются тонкими
- логика работы с БД — в моделях
- шаблоны чистые
- валидация явная
- SQL использует подготовленные запросы
- код читается и поддерживается вручную
- реализация соответствует спецификациям проекта и текущей фазе
